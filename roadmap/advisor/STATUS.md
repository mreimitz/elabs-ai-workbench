## Phase 2 — Grade-aware
- [x] WP 2.1 — quality-validated trims, skill-effect summaries, model-per-quality-bar — done 2026-08-18 · wp/advisor/2.1 (0bc84e7 · c2804c8 · 9582423 · 449ac13 + orchestrator merge-resolution 9aa81f2, merged a65789f) · spec [`phase-2-grade-aware/WP-2.1-grade-aware.md`](./phase-2-grade-aware/WP-2.1-grade-aware.md). **The "blocked" flag on this line was wrong** — benchmarks 3.4 and 5.1 are ticked done and their cores (`computeSuiteAnalytics`/`selectRunScore`, `attributeVariant`/`computeSuiteDeltas` in `suites/analytics.ts`) are exported and pure, so the WP was dispatched and is now green. Three rules on the WP 1.1 seam (`advisor.quality-validated-trim` · `advisor.skill-effect` · `advisor.model-quality-bar`, appended after WP 1.2's four, order test-pinned) + `apps/api/src/advisor/rules/grade-shared.ts` + three new read ports (`grades`/`suiteRuns`/`skills`) and an `AdvisorModelPort` over the bundled compatibility dataset. **Provenance is engine-enforced, not rule discipline:** `AdvisorRule.gradeAware` makes `assertRecommendationContract` **throw** when a grade-aware rule omits `gradeProvenance`, when a non-grade-aware rule stamps one, when the suite-run id list is empty, or when the ids are not ascending + deduped (determinism: the same finding must serialize identically). `gradingVersion` is read off the grade **rows**, never assumed to be today's constant. **A trim is refused five distinct ways**, each its own named gap: no suite-run members · members but no graded score · grade rows `unevaluable` (a NULL score is not a 0) · grades spanning two grading versions (the grading twin of Phase 1's `comparablyCounted`) · mean below the bar. One test asserts the **contrast** — over the identical fixture the Phase 1 `advisor.unused-tool-trim` still fires while this rule declines, so the gap is the rule refusing, not the fixture being empty. Judgement calls worth knowing: "score holds" = mean primary-grader score ≥ `ADVISOR_QUALITY_BAR = 0.5` — **not a new threshold**, it is the same `score >= 0.5` `SuiteAggregates.passRateAt05` already uses, and the score itself is benchmarks' `selectRunScore` (the advisor defines no score of its own); the quality-validated trim sits **alongside** the Phase 1 trim rather than replacing it (they can disagree, and this one is then the conservative answer); a cost increase is never labeled a "saving" (better-but-pricier is a trade-off in the detail); model attribution is `Scenario.model` because runs record no model (declared in the assumptions, not assumed away); `model-quality-bar` is fleet-scope only (one environment has exactly one model); windows are bounded at 20 suite runs / 10 provenance ids, both stated in the findings. **Deliberate test strengthenings:** the registry-order assertion now pins the full **seven**-rule list + order and asserts exactly the three Phase 2 rules are `gradeAware`; the empty-install route assertion goes 2 gaps → 4; the engine stub context now *forbids* the four new ports. No test deleted or weakened. No migration, no new dependency, `ASSISTANT_ENTITY_KINDS`/`SCOPE_WRITE_TOOLS`/`deriveAssistantScope` untouched (0 diff lines). **Merge resolution done by the orchestrator** (main had advanced with WP 2.2): both conflicts were "both sides appended a block at EOF" in `packages/shared` (`ADVISOR_QUALITY_BAR` + `AdvisorGradeProvenance` vs the fleet-report block) — kept both; then the two WP 2.2 call sites that construct the advisor read model (`index.ts`'s `registerReportRoutes` literal and the fleet-report test harness) were widened with the three new ports. +36 api tests.
