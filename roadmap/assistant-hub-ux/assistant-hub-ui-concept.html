1Executive summary

Your instinct is right, and it has one root cause. Every other section of the Workbench (Dashboard, Servers, Scans, Skills, Runs) mounts into the app's PageShell contract: an edge-to-edge, viewport-filling frame where the page owns its own scroll. The six Assistant routes never registered for that contract. They fall into the legacy padded, scrolling <main>, and each view compensates by drawing its own bordered, fixed-height box inside the padding. That single miss produces everything you named: boxes in boxes, half-used pages, asides that spill out of their frame, and six screens that all look like the same generic template.

The thesis of the fix: make the Assistant Hub a first-class citizen of the shell grammar the app already ships, then shape each surface for its actual job. A chat workspace, an agent library, a project library, a knowledge store, an analytics dashboard, and an event log are five different shapes. Today they are one shape. Nothing in this concept invents new UI: every proposed piece is an existing @brand/* component or an existing app-level recipe (PageShell, PageHeader, ViewToolbar, SplitPane, StatusBadge), styled by the same semantic tokens in both themes.

Five moves carry the whole redesign:

  • Adopt the shell. Register all /assistant/* routes for the full-bleed PageShell mount and delete every fixed-height inner box (min-h-[36rem], three h-[46rem] frames). Each surface fills the viewport and owns exactly one scroll region.
  • Give the workspace one meta rail, modeled on the panel you already like. Cowork's own session sidebar (Progress, Outputs, Context, with a single show/hide control in the header) becomes the pattern for the chat workspace: three stacked, individually collapsible sections in one right rail, replacing the three separate context/artifacts/files surfaces that overflow today.
  • Move session history out of the workspace. Sessions become a submenu below Assistant: a real table with states and statistics (status, mode, project, model, tokens, cost, last activity). The workspace keeps only a compact session switcher in its toolbar.
  • Rebuild Agents & Crews as the workforce section, HR-grade. A directory of named agents with real identities, an organigram view built on the app's own flow canvas, crew colors carried as a small design element, and a profile modal with left-rail sub-panels covering everything an agent is assigned: instructions, model, MCP access down to single-tool grants, skills, budgets, its own memory, and its own usage.
  • Dissolve Memory and Usage into where they belong. Memory becomes scoped: profile memory stays global, everything else lives inside project, agent, and crew detail. Usage becomes a tab of the workforce section with filter and drill-down by agent, crew, model, project, and time. The Assistant nav drops from six entries to four.

3Root cause: the hub never joined the shell

The app has a deliberate, documented shell contract. App.tsx keeps a registry of routes that mount into an edge-to-edge <main>, and PageShell then owns the gutter, the header position, and a single scroll region. The registry comment even describes the process: each migrated view adds its route as its work package merges.

// apps/web/src/App.tsx (lines 201-215, abridged)
const PAGESHELL_EXACT_ROUTES = new Set<string>([
  "/testing/environments", // WP 1.2
  "/dashboard",            // WP 2.1
  "/scans",                // WP 2.3 (master-detail, in-view split)
  "/skills",               // WP 2.8 (master-detail via SkillRail secondaryContent)
  "/servers",              // WP 2.2b (master-detail via ServerRail secondaryContent)
  "/testing/runs",         // WP 2.4
  ...                      // no /assistant route appears anywhere in this set
]);

Routes outside the registry get the legacy wrapper: <main class="… overflow-y-auto p-6"> (AppShell.tsx, line 316). The Assistant views know this. AgentsView.tsx says it out loud:

// apps/web/src/features/hub/agents/AgentsView.tsx (lines 14-17)
// Mirrors `AssistantView.tsx`'s own page-shell convention (a plain padded body, not the
// `PageShell`/`isPageShellRoute` registry — that registry is the ux-overhaul workstream's
// own migration ledger, not this workstream's) — each tab owns a bordered, definite-height
// frame so its internal `SplitPane` (list + editor) can fill and scroll correctly.

Two parallel workstreams, and the hub shipped before the shell migration reached it. Inside a padded, page-scrolling main, a chat surface cannot size itself against the viewport, so every hub view hard-codes a frame instead: min-h-[36rem] in AssistantView.tsx, and h-[46rem] in each of AgentsView, ProjectsView, and MemoryView. At 1680×1000 the measured result on /assistant is a 639 px workspace card floating in a 1000 px viewport, with roughly a quarter of the screen blank below it. The same hand-rolled header (icon, Heading, muted Text) repeats at the top of all six views instead of the shared PageHeader.

The design system itself flags the resulting pattern. The vendored kit's component notes list "Card inside a Card (nested cards): flatten" and "deep wrapper nesting inside the shell" as explicit anti-patterns. The current hub is that anti-pattern at route scale.

5The grammar that already works

You do not need a new design language. Three routes in the same app already demonstrate the target: full-bleed shell, a secondary rail for master-detail, purpose-built detail panes, and one consistent status vocabulary.

The shell machinery behind these pages is already written and documented in the codebase: PageShell guarantees a viewport-filling column, one gutter token, a fixed header slot, and three scroll modes, including scroll="fill", which exists precisely so a split view or console can own its internal scroll ("no dead sea", in the file's own words). AppShell accepts fullBleed and a secondaryContent rail. SplitPane provides the two-pane recipe with aligned pane headers. The Assistant Hub simply has to opt in.

6Target information architecture

Revision 4 consolidates the section. Memory and Usage stop being destinations and dissolve into the entities they describe, which takes the Assistant nav from six entries to four, the same move the app already made once when Testing went from seven entries to four. Nothing is lost: profile memory stays one click away, and the analytics get deeper, not shallower, by moving next to the things they measure.

The r4 model: four nav entries. Memory becomes a property of profile, project, agent, and crew. Usage becomes the workforce section's analytical tab plus small per-entity panels.

7Purpose-built surfaces

Each surface gets: a wireframe, the reasoning, the component map (every name checked against the vendored kit or the app's shared components), and what changes against today. All of them mount the same way: route registered in the PageShell set, AppShell fullBleed, no inner fixed-height boxes, one scroll owner per region. 7.1 /assistant · the chat workspace

The model for the right side is the panel you pointed at: Cowork's own session sidebar, where Progress, Outputs, and Context sit as stacked cards, each collapsible on its own, and one header control shows or hides the whole rail. That pattern maps one-to-one onto what the hub already has, and it replaces all three of today's overflow-prone surfaces (context aside, artifacts aside, files modal) with a single, well-behaved rail.

Why this shape. With sessions moved to their own page (7.2), the workspace drops to two columns: conversation plus meta rail. The transcript is the one region that scrolls; toolbar, composer, and rail stay put. The session title lives in the toolbar as a switcher (Combobox over recent sessions, with "View all sessions" and "New session" at the bottom), so switching is one click without a permanent 288 px rail. The rail toggle in the toolbar shows or hides the whole meta rail at once, exactly like the control in your screenshot; each section also collapses individually, and the collapsed state shows a count (Outputs · 3) so nothing goes invisible silently.

What each section carries. Progress: the existing per-turn task widget, and during missions the agent list with per-agent StatusBadge and stop/steer actions (the mission board card stays in the transcript; the rail is its always-visible summary). Outputs: artifacts and workspace files merged into one list (name, kind, updated, open action), which retires the separate Files dialog. Context: project link, context-window meter, budgets, sources, granted servers, attached skills, and, new in r4, the session's effective memory: the resolved stack of profile, project, crew, and agent memories that will inject into the next turn, each entry tagged with its scope and linking to where it is managed (see 7.5). All of it reads from state the app already streams; the memory stack is the one addition.

The chat canvas: a fine gradient dot grid

The conversation region gets a quiet canvas texture: a fine dot grid that fades from a light gray at the top to fully transparent before the composer, so the workspace reads as a place where work happens rather than a blank sheet, and the transcript's lower half stays perfectly clean for reading. It is one CSS layer, no image asset: a 1 px radial-gradient dot repeated on a 14 px cell, faded with a mask. The dot color is a token, not a gray value: --canvas-grid already exists in @brand/tokens for exactly this job (the flow canvas uses it), so both themes get the correct dot automatically and no raw color enters the codebase. The layer sits behind the scroll region and does not scroll with messages; it renders at the kit's normal decoration level and drops out entirely at the minimal level via the existing DecorationProvider, which keeps the §8.6 rule honest.

The first prompt: centered start, docked follow-through

A new session should not open as an empty transcript with a lonely input at the bottom. It opens as an invitation: the composer sits centered in the canvas with a short greeting above it and the page's session starters as suggestion chips beneath. The moment the first prompt is sent, the composer glides down to its docked position, the greeting and chips fade, and the transcript takes over. After that, the workspace behaves exactly as described above; the choreography runs once per session, and reopening a session with history always starts docked. Try it below.

Live preview of both ideas: the token-driven dot-grid canvas, and the composer's center-to-dock motion.

Motion spec. One property animates: the composer's position (as a transform in the real implementation, which keeps it compositor-friendly), roughly 240 to 280 ms on the app's standard curve; the greeting and chips fade over 200 ms; the first transcript bubble fades in with a slight delay so the eye follows the composer down and lands on the reply. The app already has this motion vocabulary: the hub's own panels use duration-base and ease-standard utilities, and the dock animates open and closed the same way. Reduced motion is a hard rule, not a nicety: with motion-reduce the composer starts docked and states swap instantly, matching how the shell already treats the sidebar and dock. In component terms the empty state composes ConversationEmptyState with the existing starter chips (Suggestions/Suggestion), and the timing rides BrandMotionConfig so the curve stays consistent with the rest of the kit.

7.3 /assistant/agents · the workforce section

This is the surface that earns the most design energy, and your framing is the right one: it should feel like an HR tool for a staff of AI workers. Before drawing it, a quick look at how the field handles this. Relevance AI's Workforce leans fully into the metaphor: avatar-based agent personas with functional titles, teams that own a process, tools dragged into a flow (relevanceai.com/workforce). Lindy frames deployment as onboarding a new hire: define a role, grant tool access in tiers (read-only, limited write, none), keep hard boundaries visible, review every run's trail, and expand responsibility as trust grows (lindy.ai). CrewAI's enterprise platform centers a control plane: crews and agents with tracing, run monitoring, role-based access, audit trails, and human-in-the-loop checkpoints (crewai.com). Microsoft's Copilot Studio splits agent configuration into separate knowledge, tools, and topics surfaces (learn.microsoft.com). And current agent-UX guidance stresses per-agent attribution in concurrent work, plan-step visibility, tool-use disclosure, and progressive autonomy (fuselabcreative.com). The synthesis: give agents identity, give access management real depth, give oversight its own view, and let the org be something you can see. Your app can go one step further than all of them, because it already measures MCP servers: tool grants here can show the token cost of every tool you switch on.

The section becomes three tabs under one PageHeader: Directory (the people view), Org chart (the structure view), and Usage (the analytics view, absorbing the old Usage page).

Identity first: agents get names

An agent card that reads "Research Analyst, digs through scan results" is a form entry. "Nova · Research Analyst" is a colleague. r4 adds a display name distinct from the role title (persona names are optional and freely editable; the examples here are illustrative), an avatar with the existing RoleAvatar plus a crew-color ring, and a one-line description. Everything assigned to the agent (model, servers, tools, skills, budgets, memory) hangs off that identity in the profile modal below.

Crew colors, small by design

Each crew picks one of five crew colors mapped to the theme-aware chart tokens (--chart-1 … --chart-5), so both themes stay correct and no raw color enters the code. The color appears only as small elements: a 3 px top border and avatar ring on cards, a dot beside crew names in the rail and tables, a tinted border on the org chart's crew container. Never as a fill, never as text color, always paired with the crew's name so color is redundant, not load-bearing (the kit's own Badge rule). An agent in one crew carries that crew's color; an agent in several crews shows stacked dots in the all-agents scope and the local crew's color inside a crew scope. A sixth crew reuses the palette; if that happens often, extending the token set is a theme decision, not a component hack.

The organigram is where the HR feeling lands, and the app already owns the machinery: @brand/flow ships CanvasShell (token-driven canvas on the same --canvas-grid dots as the chat), FlowGroupNode for containers, FlowNode with title, subtitle, icon, and tone, smart edges, minimap, zoom controls, and useAutoLayout; SkillFlow already renders graphs with it in this very app. Each crew is a group container tinted with its crew color; members render as avatar nodes inside. The detail that makes this more than decoration: the arrows inside a crew show its actual topology. A pipeline crew reads as a chain, a parallel crew as a fan, a debate crew as two nodes facing each other, best-of-N as a fan-in to a judge node. The org chart doubles as an honest preview of how the crew will execute, which no generic HR tool could draw. Version 1 is read-and-navigate (select shows an InspectorPanel summary, double-click opens the profile); dragging an agent between crews as a reassignment gesture is a natural follow-up once the read view proves itself.

7.5 Memory · scoped to what it describes

Your instinct restructures this cleanly. Revisions 1 to 3 kept Memory as one global page; r4 splits it by owner. Profile memory stays global: facts about you and standing instructions that inject into every conversation. 8Cross-cutting contracts

8.1 The shell and scroll contract

Conceptually the migration is one ledger entry plus deletions. The six routes join the PageShell registry (exact paths, plus an /assistant/agents/ prefix once the library gets node URLs), which flips their <main> to edge-to-edge. Each view then mounts a PageShell with the scroll mode that fits its shape: fill for the workspace and the two master-detail libraries, content for Memory, Usage, and Audit. Every min-h-[36rem] and h-[46rem] frame is deleted rather than adjusted; after the shell owns the height there is nothing left for them to do. The rule going forward is the one the codebase already states: PageShell owns gutter and scroll, so no view wraps it in another padded or scrolling box.

8.2 One header grammar

Two header variants cover all six surfaces, both already in the codebase. Library and analytics pages use PageHeader: title, one-line description, actions on the right (New, date range). Console-like pages (workspace, audit) use the headerVariant="toolbar" slot with ViewToolbar, where the working object's name is the title. The six hand-rolled icon-plus-heading blocks are deleted, and page identity comes from the breadcrumb and nav state, which the shell already renders. Titles stop moving between routes; that is the contract's stated guarantee.

8.3 The meta-rail rules (the aside fix, generalized)

  • Side information is one rail, a real sibling column: fixed width (360 px), shrink-0, its own scroll, never an overlay inside a content card.
  • The rail hosts stacked, individually collapsible sections (Progress, Outputs, Context in the workspace), and the page header carries exactly one control that shows or hides the whole rail, the pattern Cowork's own session panel uses.
  • A collapsed section keeps a count in its header (Outputs · 3) so state changes stay visible without opening it.
  • Under the width floor (~1100 px of content), the rail demotes to a right-anchored Sheet with identical content.
  • Rail content never assumes width: labels truncate with tooltips, meters measure their container. Mid-word clipping is a bug by definition.

8.4 One status vocabulary

The kit ships StatusBadge with a fixed state set (pending · running · complete · awaiting-approval · denied · failed · skipped) and the app already uses it on the reference pages. The hub maps onto it instead of inventing chips per view:

8.5 One empty-state pattern

Exactly one EmptyState per region, with one primary action, phrased as the next step ("Start a new session", "Create your first role", "No events in this range · Reset filters"). Never two dashed boxes on one screen; a list that is empty while its detail pane is also empty shows the message once, in the detail pane, exactly as /scans does. Loading uses StatePanel kind="loading", errors use ErrorState with a retry, and both fill their region so nothing floats in a void.

8.6 Density and decoration

The hub inherits the app's existing table and toolbar recipes (DataTable with the render-prop toolbar, SplitPanePanel headers) rather than restyling them. The kit's decoration rule applies as-is: decoration density goes down as information density goes up, so the dense surfaces (audit, usage table, tool grants) stay chrome-free, and the one place that earns visual richness is the conversation itself. That is exactly where the two r3 touches land: the dot-grid canvas (a --canvas-grid-token layer, gated by DecorationProvider) and the first-prompt composer motion (standard curve, motion-reduce honored). Neither appears on any data surface.

9Both themes

Because the concept is composed entirely of @brand/* components bound to semantic tokens, both themes come along automatically: surfaces sit on --background/--card/--surface-*, rails on the --sidebar-* family, chat bubbles on --chat-user/--chat-assistant, charts on --chart-1…5, and status colors on --success/--warning/--destructive/--info with their -text pairs for contrast. The concept introduces no raw colors, no dark: overrides, and no new component kit; if a surface reads wrong in one theme, the fix is a token, not a view. The kit's third theme (blueprint) is unused by this app and stays out of scope.

10Open questions and trade-offs

  • Open-on-double-click semantics. The directory uses click to select and double-click, Enter, or the card menu to open settings. If you find yourself always opening, an alternative is click-to-open with selection via checkbox hover (the pattern file browsers use). Worth deciding after a week of real use.
  • Does the meta rail remember per-section state? Recommended: yes, per session mode (chat vs mission open different sections by default; Progress matters most mid-mission, Context most in chat). The alternative is one global remembered state, simpler but blunter.
  • Rail width: fixed or resizable? The App-assistant dock already ships a drag-to-resize recipe (300 to 720 px, persisted). Reusing it adds polish but also a second resizable region. The concept starts fixed at 360 px and treats resize as a follow-up.
  • Sessions table scope. Should it include mission child-agent sessions or only top-level chat/research/mission sessions? The concept says top-level only, with child agents visible through the mission's own board and Usage; a "show agent sessions" toggle is the escape hatch if you miss them.
  • Audit: table or feed? The concept keeps the table for scale and adds day grouping. If you find yourself reading audit as a story rather than querying it, RevisionTimeline compact is the ready alternative; both consume the same rows.
  • Where does "New session" live globally? With the workspace header now a toolbar, a global "New session" could also join the command palette (⌘K) as a first-class action. Cheap, but it touches the palette's action registry, which is outside the hub.
  • Usage attribution needs API honesty. The endpoint accepts from/to/projectId today but nothing exercises them, and per-agent/per-crew attribution from mission events is new query work. The Usage tab should ship with an explicit "no agent" bucket for unattributed spend rather than a silently incomplete total.
  • Agents/Crews URL scheme. Node-level URLs (/assistant/agents/agent/:id, …/crew/:id, plus tab and drill state in the URL) make the workforce section deep-linkable like servers. Worth it, in my view: Audit and the Usage drill both want to link at agents.
  • Org chart: when does it become editable? Version 1 is read-and-navigate. Drag-an-agent-between-crews as a reassignment gesture is the obvious v2, but it needs move semantics (what happens to topology position and crew-scoped memory on move) decided first.
  • Crew palette size. Five crew colors from the chart tokens cover the near term; a sixth crew reuses colors. If more distinct crews become normal, extending the token palette is a theme decision to make once, upstream.
  • Memory precedence. When profile, project, crew, and agent memories conflict, which wins? The concept assumes most-specific-wins in injection order and shows the stack transparently in Context, but the rule (and whether conflicts should warn) deserves an explicit decision.
  • Persona names: optional or default? The directory reads best when agents have display names, but auto-generating them may feel gimmicky. The concept makes the name field optional with the role title as fallback; revisit after living with it.
  • Known bugs to file regardless of this concept: the silent "Create role" no-op; the runs feed stuck on loading in this environment; the Autonomy helper text clipping; the session-rail label truncation.
