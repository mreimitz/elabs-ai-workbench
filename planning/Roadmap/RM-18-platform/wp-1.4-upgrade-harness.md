## 1. Verify at pickup — most of the surface already exists

**Do not rebuild what is there.** `apps/api/test/migrations.test.ts` is already **~2,940 lines**,
plus `migration-v16-e2e.test.ts` (~390). Read both before writing a line. Your job is the
**residual**, and the residual is a specific, verified weakness — not "add migration tests".

**The weakness, confirmed by reading the file:** every "old database" in the existing suite is
*simulated by rewinding a new one*. The pattern is always the same — create the DB at the latest
shape from `schemaSql`, then `DROP TABLE`/drop a column/drop an index and re-stamp
`PRAGMA user_version` backwards. Examples on disk: `":491"` *"simulate a pre-v42 (v41) DB by
rebuilding `runs` WITHOUT the lineage columns"*, `":546"` *"…then rewind to a pre-v43 (v42) DB"*,
`":841"` *"simulate a pre-v20 (v19) DB lacking them"*.

That method tests the migration against **the test author's belief about the old shape**, not
against a shape that ever existed on disk. It is structurally blind to:

- a column whose old `CHECK` constraint or `DEFAULT` differed from today's;
- an index that existed under a different name, or a table whose DDL column order differed;
- the **pre-versioning** database (`user_version = 0`), which is the one real upgrade path this app
  actually shipped and which no rewind can reconstruct faithfully;
- data shapes real usage produced (NULLs where the current code never writes NULL, legacy JSON
  envelope versions, rows orphaned by a since-removed feature).

`LATEST_SCHEMA_VERSION` is derived from the last `MIGRATIONS` entry and is currently **61**.

## 2. What to build

### (a) A fixture generator script

A committed script that produces each fixture database deterministically — so a fixture can be
regenerated and reviewed rather than being an opaque blob nobody dares touch. Suggested home:
`apps/api/scripts/` (match whatever convention the repo already uses; do not invent a new top-level
folder).

For each captured version the script must produce a **small** database (kilobytes, not megabytes)
that is stamped at that `user_version` and carries **a handful of representative rows in the tables
that migration touches** — the rows are the point; an empty schema proves almost nothing.

### (b) The captured fixtures, committed

Binary `.sqlite` artifacts under a fixtures folder (e.g. `apps/api/test/fixtures/upgrade/`), each
named by the version it is stamped at. **Cover, at minimum:**

- `user_version = 0` — the pre-versioning shape (the real historical starting point);
- **pre-v13** as the item's own row names;
- and each version at which a migration makes a **non-trivial, data-bearing** claim — a backfill, a
  table rebuild, a CHECK widening, a seed. `v16` (collections + the `Local` seed), `v27`
  (`ratingState` backfill), `v44` (`model_pricing` seeded from code), `v59` (the cache-token
  backfill from `run_steps`) and `v61` are the obvious ones; read `MIGRATIONS` and justify your set
  in the report rather than guessing.

You do **not** need a fixture per version 1…61. Say in your report which versions you captured and
**why the ones you skipped are trivially additive** — a skipped version must be a defensible call,
not an omission.

### (c) The harness

A test that, for **every** fixture: opens it, records its `user_version`, runs `applyMigrations`,
and asserts a set of **invariants** that hold regardless of which fixture it started from:

- `user_version` ends at `LATEST_SCHEMA_VERSION`;
- migrating a second time is a **no-op** (idempotence) — run it twice, assert the schema and the
  row counts are unchanged;
- **no row is lost**: every table's count is ≥ its pre-migration count, and specific seeded rows are
  still findable by id with their pre-migration values intact;
- `PRAGMA foreign_key_check` and `PRAGMA integrity_check` come back clean;
- the resulting schema **matches a freshly created one** — compare the migrated database's
  `sqlite_master` against a DB built straight from `schemaSql` + `applyMigrations`, normalized for
  whitespace. This is the assertion that catches "the migration path and the baseline schema have
  drifted apart", which is the failure mode a rewind test can never see;
- the app can immediately **use** the result — at least one repository read per major area
  (`ScanRepository`, `RunRepository`) returns without throwing.

It runs in `pnpm test` like everything else, so a future migration that breaks an old database
fails the gate rather than a user's install.

### (d) Documentation

A short `README.md` **beside the fixtures** (not in `planning/`, where README files are banned) that
says what each fixture is, how to regenerate it, and how to add one for a new migration.

## 3. Rules that bind this WP

- **API-side only.** No `packages/shared` change, no `apps/web` change, no new route, no wire change.
- **Do not add a migration**, and do not edit `MIGRATIONS` or `schema.ts` to make a fixture pass —
  if a real migration defect turns up, that is a **finding to report**, not a thing to paper over.
  Fix forward only if the fix is unambiguously correct, and say so loudly in the report.
- No new runtime dependency. `better-sqlite3` and the node test runner are already there.
- Fixtures are committed artifacts: keep them small, and make sure nothing in them looks like a
  secret (they must carry no real credential, encrypted or otherwise — generate rows, never copy
  from `data/app.sqlite`).
- **Never touch `data/app.sqlite`.** Work only on files you create under the fixtures folder.

## 4. Acceptance

- [ ] A committed script regenerates every fixture deterministically; running it twice yields
      byte-identical files (or the report explains precisely why it cannot and what varies).
- [ ] Fixtures are committed, small, and include `user_version = 0` and a pre-v13 database.
- [ ] The harness runs every fixture through `applyMigrations` and asserts all six invariant
      classes in §2(c), including the migrated-vs-fresh `sqlite_master` comparison.
- [ ] Idempotence is proved by running the migration twice, not by reading the code.
- [ ] The harness is part of `pnpm test` — no separate command, no opt-in flag.
- [ ] A README beside the fixtures documents regeneration and how to add one.
- [ ] `MIGRATIONS`, `schema.ts` and every existing test still pass unmodified — or any change to
      them is called out explicitly in the report with its justification.
- [ ] Gate green from the repo root: `pnpm typecheck && pnpm test && pnpm build && pnpm lint`.

## 5. Out of scope

- The first-run demo seed (WP 1.1), in-app docs (1.2), the diagnostics bundle (1.3), the
  performance pass (1.5).
- Migrating anything in production, or touching the owner's live database.
- Adding a new migration of any kind.
