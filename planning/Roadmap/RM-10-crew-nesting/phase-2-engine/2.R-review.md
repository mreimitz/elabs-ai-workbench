## Verdict — all ten probes **REFUTED**. No `2.fix` created.

Every one of the ten probes was mounted as a **concrete deterministic attack** (not an inspection) in
`apps/api/test/hub-crew-nesting-wp2r-review.test.ts`
— 17 subtests, all green, driving the injectable stub-runner seam (no provider key, no real child
process, no MCP server). Each attack failed to break its invariant; the invariant is **REFUTED** and
cited below against the product `file:line` that enforces it. **No probe produced a FINDING, so no
`WP-2.fix-*.md` spec and no STATUS `blocked` line were authored** (the orchestrator appends the review
outcome to `STATUS.md`; this WP does not touch it).

Two D-CN decisions were placed under the most adversarial scrutiny the spec demanded and both held:
the **empty-crew-ref grant** decision (probe 7) cannot be exploited to escalate, and the WP 3.1
sub-mission **`plan_proposed` event** does **not** route a child through the propose gate / HITL /
auto-approve (probe 6). Details in those two probes below.

Read-only-on-product-code invariant met: `git diff --name-only` touches only the new test file and
`roadmap/crew-nesting/*` (proof in the WP 2.R report to the orchestrator).

## Probe 1 — Budget monotonicity (D-CN3) · **REFUTED**

**Attack.** A branchy N×M tree (root `parallel` of two crew-refs, each a crew of three `$1` leaves)
whose per-child saved `maxCostUsd` is set *far above* its fair share (`$1000` each), plus a variant
where a child names **the whole env ceiling** (`maxCostUsd === caps.maxBudgetUsd = 500`). Assert the
aggregate spend can never exceed the root `min(requested, HUB_MISSION_MAX_BUDGET_USD)`, and that a
child never re-reads `caps.maxBudgetUsd`.

**Result.** The monotone allocation primitive `allocateChildBudget(req, remaining) = max(0, min(req,
remaining))` — which takes **no `caps` argument**, so it is structurally incapable of re-reading an env
ceiling — bounds every hand-down to the parent's remaining pool. The `$1000`/`$500` requests were
clamped to the parent's remaining ($4/$2); the second sibling was starved to `$0` (R3c). Aggregate
spend stayed `≤` the root ceiling in every variant.

- Enforced by: `allocateChildBudget` `planner.ts:359` (`../../../apps/api/src/hub/missions/planner.ts`);
  the synchronous at-spawn reservation `childCap = allocateChildBudget(childRequested, level.budget.reservable); level.budget.reservable -= childCap`
  `orchestrator.ts:1299` (`../../../apps/api/src/hub/missions/orchestrator.ts`); the shared tree-wide
  trip `for (const ab of leafAborts) ab.abort()` `orchestrator.ts:913` (`../../../apps/api/src/hub/missions/orchestrator.ts`)
  fired by `if (runtime.budget.cap > 0 && runtime.cost.total >= runtime.budget.cap) runtime.tripBudget()`
  `orchestrator.ts:1201` (`../../../apps/api/src/hub/missions/orchestrator.ts`); the root-only ceiling
  clamp `maxCostUsd: Math.min(requestedCostUsd, caps.maxBudgetUsd)` `planner.ts:648` (`../../../apps/api/src/hub/missions/planner.ts`).

**Precise scope note (not a FINDING).** The load-bearing D-CN3 property — `sum(child allocations) ≤
parent.maxCostUsd`, hence aggregate *allocation* ≤ root ceiling — holds **strictly**. Actual aggregate
*spend* holds in the pre-existing "stop-launching once crossed" sense: the trip is checked *after* a
leaf's cost is added (`orchestrator.ts:1201` (`../../../apps/api/src/hub/missions/orchestrator.ts`)), so
the single leaf that crosses the cap (and any others already in flight) still counts, bounding overshoot
to ≤ `maxParallel` leaves' cost. This is **identical to a flat (non-nested) mission's** long-standing
trip behavior — crew nesting does **not** amplify it, because the shared tree-wide accumulator + shared
trip are the ceiling, and the shared limiter caps concurrent leaves at the root `maxParallel`. The
probe-1 tests therefore rig evenly-dividing leaf costs (the same discipline the existing WP 2.1/2.2
suites use) so the strict spend bound is asserted honestly.

infinite recursion / stack overflow). A loud `warn` naming the circular reference was logged.

## Probe 7 — Transitive grant intersection + the empty-crew-ref decision (D-CN9/D-HF5) · **REFUTED**

**Attack — the CRITICAL scrutiny of WP 2.3's empty-crew-ref decision.** WP 2.3 treats an *entirely-empty*
crew-ref grant as "no added restriction" (it passes the enclosing scope through unchanged). Three
escalation attacks were mounted against that decision:

1. **Two empty crew-refs deep** — the root scope drops server `gamma`; two nested empty crew-refs sit on
   the path; a **level-3** role's own Access grants `gamma`, `beta:"all"`, `alpha:[read,write]`. Assert
   `gamma` is *still absent* at level 3. **Result:** the level-3 child's `toolScope` equalled the exact
   transitive intersection `effectiveAgentGrants(leaf, rootScope)` — `gamma` absent, `beta` narrowed to
   `[read]`, builtins narrowed. The empty passthrough **composes** through two levels and never re-widens.
2. **Explicit narrowing binds through a deeper empty crew-ref** — a level-1 crew-ref narrows `vendor` to
   `[search]`; a level-2 *empty* crew-ref sits below it; a level-3 role wants `vendor:"all"`. Assert the
   grandchild is bound to `[search]`. **Result:** level-3 `toolScope.servers === { vendor: ["search"] }` —
   the explicit narrowing binds through the empty crew-ref; the broad grandchild role cannot re-widen.
3. **Pure-function surface** — an empty grant fed to `effectiveAgentGrants` **as the plan** drops *all*
   servers (the safe direction — a tool-strip, never wider); a broad plan can never re-add a server the
   enclosing scope dropped. `subCrewParentScope` special-cases the entirely-empty grant to return the
   enclosing scope *unchanged* — which is `⊆` the enclosing scope by construction, **never wider**.

None escalated. The empty-crew-ref decision is **safe**: `subCrewParentScope` returns either the enclosing
scope itself (empty case) or `effectiveAgentGrants(crewRefGrants, enclosingScope) ⊆ enclosingScope` — so
the threaded parentScope is never wider than the enclosing scope, and every level-N agent still intersects
its own grants against it. A builtins-only crew-ref (which routes through `effectiveAgentGrants`) actually
**over-restricts** (drops all servers) — a safe-direction quirk, not an escalation.

## Probe 8 — Transitive autonomy non-escalation (D-CN9) · **REFUTED**

**Attack.** A nested tree under an `always_ask` parent; assert autonomy is `min` down the path — a nested
level can never loosen the parent's `always_ask`.

**Result.** Every mission in the tree (root + both nested levels) ran at `always_ask`. Structurally, a
`HubCrew` carries **no independent autonomy field**, and `runSubCrew` always instantiates + creates the
sub-mission with `autonomy: mission.autonomy` (the parent's dial); the clamp additionally pins any plan
that declares `auto` back to the mission autonomy. So a nested `auto` cannot raise the parent's
`always_ask`, and the whole tree is uniform at the root dial.

- Test: `PROBE 8 REFUTED — every sub-mission inherits the parent's always_ask; a nested tree can never loosen autonomy down the path`.
- Enforced by: `autonomy: mission.autonomy` on the child plan and row
  `orchestrator.ts:1276` (`../../../apps/api/src/hub/missions/orchestrator.ts`) /
