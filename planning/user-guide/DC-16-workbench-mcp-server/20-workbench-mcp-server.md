# 20. The workbench agent playbook — let an AI read your workbench

Everything the app measures — scans, footprints, sessions, grades, skills, suites — normally lives
behind the screens in this guide. This page is about the other door: the workbench can hand all of
it to an **AI agent** over the same standard protocol it analyses, so you can ask questions in a
chat window instead of clicking through views.

If you have ever wanted to type *"which of my servers got more expensive this month, and did any
session actually fail because of it?"* and get an evidenced answer, this is how.

## What this buys you

The workbench speaks **MCP** — the same protocol its analysis is about. Turn a coding assistant
like **Claude Code** or **Cursor** at it and that assistant can read your measurements directly:

- **Answers instead of navigation.** "What's the most expensive tool on my Filesystem server?" is
  one question, not a scan page, a sort, and a squint.
- **Your evidence, in the place you're working.** An assistant helping you edit a skill can pull
  that skill's real token footprint and security surface from this app while it works, rather than
  guessing.
- **Automation without a browser.** A build pipeline can ask the same questions your screen does
  and act on the numbers.
- **No copy-paste, no export step.** The assistant reads the live database through the app, so the
  answer reflects what the app knows right now.

Mostly it reads. Three things it can also **do** — run a scan, start a suite, launch a run plan —
are locked behind permissions you hand out yourself: see
[What an assistant can actually do](#what-an-assistant-can-actually-do).

## Point an assistant at it

The workbench serves this at **`http://127.0.0.1:8080/api/mcp`** when you run it with
`pnpm dev`/`pnpm start`, or **`http://localhost:8081/api/mcp`** when you run the Docker container.
Use whichever address you normally open the app on, with `/api/mcp` on the end.

**Claude Code** — one command in any project:

```bash
claude mcp add --transport http workbench http://127.0.0.1:8080/api/mcp
```

**Cursor, Claude Desktop, and other hosts with a JSON config** — add one server entry:

```json
{
  "mcpServers": {
    "workbench": { "type": "http", "url": "http://127.0.0.1:8080/api/mcp" }
  }
}
```

**Anything else.** Open `http://127.0.0.1:8080/api/mcp/llms.txt` in a browser. That page is written
for machines and generated by the running server, so it always lists exactly the tools that instance
offers, how to connect, and the rules they follow. Hand it to any agent that asks "what can you do?"

The app must be running. On the same machine, that is all it takes — no credential, no setup.

## Connecting from another machine

If the assistant runs somewhere else — a colleague's laptop, a CI runner, a container on your
network — it needs a **[service token](../DC-17-service-tokens/21-service-tokens.md)**, the same one every other remote
caller of this app needs. Two things to get right:

1. **Tick "Read" when you create the token.** Reading is the price of admission here: an assistant
   cannot even ask "what can you do?" without it, because listing the tools *is* a read. A token
   without Read is refused at the door, before it sees a single tool.
2. **Put the token in the assistant's own config**, as an `Authorization` header. Most hosts have a
   `headers` block beside the URL:

```json
{
  "mcpServers": {
    "workbench": {
      "type": "http",
      "url": "http://192.168.1.20:8081/api/mcp",
      "headers": { "Authorization": "Bearer mcpfp_your_token_here" }
    }
  }
}
```

Claude Code takes the same thing on the command line:

```bash
claude mcp add --transport http workbench http://192.168.1.20:8081/api/mcp \
  --header "Authorization: Bearer mcpfp_your_token_here"
```

**Read is not the whole story any more.** Three tools on this door *act* rather than read, and each
one needs its own extra permission **on top of** Read — never instead of it:

| If you want the assistant to… | Tick |
| --- | --- |
| Read your measurements (and connect at all) | **Read** |
| Start a discovery scan of a registered server | **Read** + **Run scans** |
| Start a saved benchmark suite | **Read** + **Run suites** |
| Launch a collection or ad-hoc run plan | **Read** + **Launch runs** |

Tick nothing but Read and the assistant is a reader — it will be refused, politely and in words, the
moment it tries to start anything, and the refusal names the exact permission it is missing so it can
ask you for it. That is the point: **the permission you tick is the consent you give.** An assistant
working unattended has nobody to ask before it spends money, so the only approval it gets is the one
you gave when you created its token.

If you would rather the local machine needed a token too, that is the `API_AUTH_REQUIRED` setting
described on the [service tokens](../DC-17-service-tokens/21-service-tokens.md#locking-down-the-local-machine-too) page.
It applies to the whole app, this door included — there is no separate switch just for here.

## Worked examples

Questions an assistant can answer once it is connected. Nothing here needs you to know an id, a
table, or a screen — the assistant starts from a list and drills in.

- *"List my MCP servers and tell me which one costs the most tokens before a model has done any
  work."*
- *"Take my newest scan of the Filesystem server. Which five tools are the most expensive, and what
  share of the total are they?"*
- *"Will that server fit inside GPT-5 and Claude Haiku, or will it strain them?"*
- *"Show me the test runs that failed this week, then explain what went wrong in the last one."*
- *"Pull the full report for that run and summarise the grades."*
- *"What does my `pdf-tools` skill cost, and does it bundle any scripts or reach out to the
  network?"*
- *"Compare the latest suite run's members — which combination was most expensive per graded
  point?"*

Two habits make the answers better: name a real thing ("the Filesystem server", "the pdf-tools
skill") so the assistant can find it, and ask it to **cite the numbers** it used, so you can check
them on the matching screen.

## What an assistant can actually do

Most of this door reads. **Three** tools act, and only if you gave the token the matching permission:

| Tool | What it does | What it costs you | Needs |
| --- | --- | --- | --- |
| **Run a scan** | Connects to one of your registered MCP servers and re-measures its tool surface | Time — a real connection to that server, taking as long as that server takes | Read + **Run scans** |
| **Start a suite** | Runs a saved benchmark suite's whole matrix (its tests × environments × repetitions) | **Money** — real provider tokens, against whatever cost caps that suite sets | Read + **Run suites** |
| **Launch a run plan** | Runs a collection's tests, or an explicit list of tests, against chosen environments | **Money** — same as above | Read + **Launch runs** |

Two habits of these three tools are worth knowing, because they change how a conversation goes:

- **They hand back a receipt, not a result.** Starting a suite returns its id straight away and the
  assistant polls for progress; it does not sit there holding the conversation open for twenty
  minutes. A scan is the exception — scans are quick, so that one does wait, and tells you whether it
  succeeded or failed rather than quietly reporting zero tools.
- **They tell the assistant what it is about to spend.** Every launch comes back with the same
  advisory cost estimate the app's own launcher shows you on screen, so an assistant can say "this
  will be roughly N runs and about $X" before you say go. It is advice, not a brake: it never blocks
  a launch, and a model with no price on file is reported as *unpriced* rather than as free.

Whatever permissions you hand out, connected assistants **cannot**:

- **delete anything** — no scan, run, server, skill, or collection, at any permission level. There is
  no delete on this door and there never will be;
- change any setting, edit a server, a skill or a collection, or create or revoke a token;
- see a secret. Server credentials, request headers, and GitHub tokens are never returned — an
  assistant can see *that* a server has a secret configured, never what it is.

If you want an assistant that can *edit* things on your behalf inside the app, that is the built-in
[App assistant](../DC-12-app-assistant/12-assistant.md), which asks you for approval each time rather than up front.

## Turning it on and off

The door is a feature switch like any other: **Settings › Features › Workbench MCP server**.

Turn it off and the endpoint stops answering immediately — a connected assistant, a stale terminal,
or a script all get a plain "this feature is turned off" refusal, and the setting survives a
restart. Nothing else in the app changes: this feature has no screen and no menu entry of its own,
so switching it off simply closes the door.

Turn it back on and connected assistants can reconnect without any further setup.

## What it costs a model

Every MCP server a model connects to spends part of the model's context just *describing itself* —
which is the cost this whole app exists to measure. The workbench holds itself to the same standard
it holds your servers to: its own description is kept under a **3,500-token budget**, and a check
that runs with the test suite scans this very endpoint with the app's own scanner and fails if it
grows past it. The current measurement is **24 tools costing 3,183 tokens**.

That budget was 3,000 until 2026-08-20, when it was raised deliberately to pay for **describing every
parameter**. The mount previously declared 49 parameters with no description at all — which the app's
own security analyzer reported, correctly, 49 times: an agent could not tell whether `runs_list`'s
`since` wanted a timestamp or a run id. The descriptions cost 434 tokens; the alternative was leaving
them undescribed to keep a number under a line we drew ourselves, which is exactly what we would
criticise a vendor for. The mount now scores **100/100** against its own analyzer.

You can reproduce that number yourself from the project folder:

```bash
pnpm mcp:self-scan
```

It writes a footprint report (JSON and Markdown) under `.artifacts/mcp-self-scan/` and prints the
measured total.

## What is not here yet

Being honest about the edges:

- **Actions are the three above, and no more.** Editing a server, a skill, a scenario or a setting
  over this door is not built, and deleting never will be. Use the app, or the
  [App assistant](../DC-12-app-assistant/12-assistant.md), for anything else that changes something.
- **No "wait for it" mode.** An assistant that starts a suite has to poll for the result. There is no
  tool that blocks until a matrix finishes, deliberately — a stuck conversation is worse than a
  receipt.
- **One token, not one per assistant.** A [service token](../DC-17-service-tokens/21-service-tokens.md) identifies a
  *caller*, not a person. Two assistants sharing a token look identical in the log; give each its own
  if you want to tell them apart.
- **Local only.** Sharing a workbench with a team — accounts, roles, who-did-what — is a separate
  piece of work.
