# MCP Token Footprint — UI structural audit & fix list

> **Historical record.** This document reports what was observed on the date in its title, against the pre-v4 `@brand/*` design system, when the kit shipped six themes (`qlik-bright`, `qlik-dark`, `light`, `dark`, `blueprint`, `high-contrast`). The project now runs `@elabs-ai/components-*` v4, which ships exactly two — `light` (default) and `dark`. Theme names and counts below are preserved as observed and are NOT current. See [`.claude/rules/styling-and-tokens.md`](../.claude/rules/styling-and-tokens.md).

_2026-06-20 · live app at http://localhost:8080/, all five views, driven via agent-browser._
_Assessed with the `qlabs-enterprise-ui` skill lens (screen-layout-patterns, object-and-navigation, enterprise-app-baseline)._

## TL;DR

The app is in **good shape** — noticeably better than earlier screenshots suggested.
Several views are already exemplary. The remaining defects are concentrated in the
**Server detail page chrome** (nothing sticks; the two panes scroll with the page) plus
two **global baseline** gaps (theme control, settings entry). Every item below maps to a
fix the skill already prescribes.

## What's already good — protect these

- **App shell** is consistent: sidebar (Dashboard/MCP Servers/Scans/Compare/Settings) +
  top bar with breadcrumb + Refresh + theme.
- **Scans** — a clean master-detail split (history list left, detail right) with a proper
  "Select a scan" empty state.
- **Compare** — a simple Selection form (Server/Before/After) + "Pick two scans" empty state.
- **Server detail** — uses **Tabs** (Tools / Overview / Scans); a KPI `MetricCard` row; and
  the **tool master-detail is side-by-side and updates in place** (clicking a tool updates
  the right pane — the previously-reported "detail below the list" is **resolved**).
- **Dashboard** — a routing surface (KPI row + latest-server-footprint + recent-scan tables).

## Findings & fixes (prioritized)

### P0 — Server detail: header, action toolbar, and the Tab bar all scroll away
**Symptom.** On the server detail, scrolling the Tools content scrolls the whole page —
the server name, the Edit/Test/Run scan/Delete actions, the KPI row, and the **Tab bar
(Tools/Overview/Scans)** scroll out of view. To switch tabs or run a scan you must scroll
back to the top. (Verified: after a 600px scroll only the app top-bar remained.)
**Why it matters.** Loss of orientation; the primary actions and the section nav become
unreachable while working (rulebook R012/R022).
**Fix (brand-ui).**
- Wrap the detail in `PageShell`; put the title + status badges + the action `ButtonGroup`
  in a **sticky** `SectionHeader`.
- Keep the **`TabsList` in the sticky region** (header or a sticky sub-bar) so the tab bar
  stays while only `TabsContent` scrolls.
- Give the detail a fixed-height layout (`flex min-h-0` / `h-[calc(100dvh-…)]`) so the chrome
  doesn't participate in the scroll.
**Ref.** `screen-layout-patterns.md` → "Anatomy of an object detail page".

### P0 — Server detail: the master-detail panes scroll with the page, not independently
**Symptom.** The tool list (left) and tool detail (right) live in the page scroll; scrolling
moves both, so you can't keep the list in view while reading a long tool detail.
**Why it matters.** Defeats the point of master-detail (scan + read simultaneously); pairs
with the P0 above.
**Fix.** Render the Tools tab as a fixed-height `SplitPanel` (`start`=tool list,
`end`=tool detail, `startSize="360px"`), each pane wrapped in its own `ScrollArea` so they
scroll independently. The split sits **inside** the non-scrolling detail region (depends on
the sticky fix).
**Ref.** `screen-layout-patterns.md` → "Master-detail".

### P2 — Server header actions are loose, not a toolbar
**Symptom.** Edit / Test / Run scan / Delete are individual buttons in a row; Delete is an
icon-only trash with no visible label.
**Fix.** Group them in a `ButtonGroup` (Run scan = primary; Delete = `destructive` variant,
separated by `ButtonGroupSeparator`); give the icon-only Delete an `aria-label` + `Tooltip`;
route Delete through an `AlertDialog` confirm.
**Ref.** `screen-layout-patterns.md` component table; principles R084/R085.

### P2 — Server rail (the list) has no search/filter
**Symptom.** The "Registry / 4 configured" rail has Add (+) and a count, but no search;
it won't scale past a handful of servers.
**Fix.** Add a `SearchInput`/filter above the server cards; keep the count as a header/footer.
Promote to a `DataTable` if the list grows large.
**Ref.** `screen-layout-patterns.md` → "list page"; rulebook R074.

### P1 — Theme control is light/dark only, not System / Qlik Bright / Qlik Dark
**Symptom.** The top-bar theme button toggles light ↔ dark (sun icon); it does not expose
the baseline's System / Qlik Bright / Qlik Dark.
**Fix.** Use the library `<ThemeSwitcher />` — its `themes` defaults to the the vendor light/dark
pair and `showSystem` defaults to `true`, so it renders **System / Qlik Bright / Qlik Dark**
out of the box.
**Ref.** `enterprise-app-baseline.md` §1b; `shell-and-navigation.md` §3b.

### P2 — Settings is a full route; no quick settings modal / Appearance section
**Symptom.** Settings is a nav route (token profile + app info). There's no always-available
settings modal, and theme lives only as a top-bar toggle (no Appearance section).
**Fix.** Keep the route for deep config, but add the baseline `Dialog` settings modal (gear
in the top bar) with an **Appearance** section hosting the theme switcher. (Optional — the
route is acceptable; the modal is the baseline ideal.)
**Ref.** `enterprise-app-baseline.md` §1c.

### P3 — polish
- Dashboard "Portfolio footprint" card reads sparse on the left — ensure a real empty/loading
  state or let it fill the space.
- Mark the **selected/visited** row in the server rail and scan history (rulebook R077).
- Confirm the detail panes keep `min-w-0` so long tool names/URLs truncate, not overflow.

## Server detail — information priority & intent (owner walkthrough)

Higher-order than the structural items above: the layout is structurally present but
**mis-prioritized** — no sense of what matters most or how the user acts on it.
Ref: the skill's `information-priority-and-emphasis.md`.

### P1 — Tab order buries the summary
Tabs are **Tools · Overview · Scans**; Overview (the at-a-glance summary) should be **first and
the default**. → reorder to **Overview · Tools · Scans**.

### P2 — Overview repeats the header KPI band
The Overview's first row duplicates the KPIs already shown in the (sticky) header. → drop the
duplicate; lead Overview with the findings instead. Say each thing once.

### P1 — Valuable findings are buried and not actionable
"Attention & Optimization" is the **most valuable** content but sits in a card-in-card with no
way to act on it. → make it the Overview **hero**: a list of recommendations, each **what + why
+ a CTA** ("schema = 88% of this tool's tokens → Review schema"). "Footprint composition" is
fine; "Top token contributors" wastes full width on a bar chart → a **compact ranked list**
(tool · tokens · inline bar · %). (insight → action)

### P0 — Tools tab: importance is inverted
The list takes **⅔**, the **detail** (the actual point) only **⅓**.
- **Rebalance:** list ~`360–400px`, detail takes the rest; each pane its own `ScrollArea`.
- **List = decision signal:** show **tokens + a detected-issues badge + status** — what helps
  you pick a tool — not a duplicated, overflowing instruction. Truncate the name/description to
  one line (tooltip for the rest); the full instruction lives **once**, in the detail.
- **Structure the detail** (it's a flat panel today): sub-`Tabs` **Breakdown / Parameters / Run
  / Raw**; one **segmented bar** for the token split (Name/Description/Schema/Annotations), not
  four stacked bars; raw JSON tucked last.

### P1 — Run Tool deserves its own surface
A high-value feature crammed into the detail panel. → promote it to a **large `Dialog`**:
parameters on the **left**, results on the **right**; show the call's token/byte cost with the
result; purposeful reveal motion. (Match the surface to the task's value.)

**One sharpening the live test surfaced** (now added to the skill): "sticky header" should
say explicitly that **the Tab bar stays in the sticky region and each master-detail pane gets
its own `ScrollArea`** — only the tab content scrolls. That nuance is the difference between
this app's "Tabs exist but scroll away" and a correct detail hub.

## How to hand this to the agent

Point your agent at this file plus the skill reference `screen-layout-patterns.md`. Suggested
order: **P0 sticky chrome + independent-scroll split** (one change, biggest win) → P1 theme
switcher → P2 toolbar / rail search / settings modal → P3 polish. Re-run the agent-browser
scroll test after the P0 fix: scroll the Tools content and confirm the title, actions, and
Tab bar stay put while only the list/detail scroll.
