# 20. The workbench agent playbook — let an AI read your workbench

Everything the app measures — scans, footprints, sessions, grades, skills, suites — normally lives
behind the screens in this guide. This page is about the other door: the workbench can hand all of
it to an **AI agent** over the same standard protocol it analyses, so you can ask questions in a
chat window instead of clicking through views.

If you have ever wanted to type *"which of my servers got more expensive this month, and did any
session actually fail because of it?"* and get an evidenced answer, this is how.

## What this buys you

The workbench speaks **MCP** — the same protocol its analysis is about. Turn a coding assistant
like **Claude Code** or **Cursor** at it and that assistant can read your measurements directly:

- **Answers instead of navigation.** "What's the most expensive tool on my Filesystem server?" is
  one question, not a scan page, a sort, and a squint.
- **Your evidence, in the place you're working.** An assistant helping you edit a skill can pull
  that skill's real token footprint and security surface from this app while it works, rather than
  guessing.
- **Automation without a browser.** A build pipeline can ask the same questions your screen does
  and act on the numbers.
- **No copy-paste, no export step.** The assistant reads the live database through the app, so the
  answer reflects what the app knows right now.

It reads. It does not act: see [The read-only guarantee](#the-read-only-guarantee).

## Point an assistant at it

The workbench serves this at **`http://127.0.0.1:8080/api/mcp`** when you run it with
`pnpm dev`/`pnpm start`, or **`http://localhost:8081/api/mcp`** when you run the Docker container.
Use whichever address you normally open the app on, with `/api/mcp` on the end.

**Claude Code** — one command in any project:

```bash
claude mcp add --transport http workbench http://127.0.0.1:8080/api/mcp
```

**Cursor, Claude Desktop, and other hosts with a JSON config** — add one server entry:

```json
{
  "mcpServers": {
    "workbench": { "type": "http", "url": "http://127.0.0.1:8080/api/mcp" }
  }
}
```

**Anything else.** Open `http://127.0.0.1:8080/api/mcp/llms.txt` in a browser. That page is written
for machines and generated by the running server, so it always lists exactly the tools that instance
offers, how to connect, and the rules they follow. Hand it to any agent that asks "what can you do?"

The app must be running, and the assistant must be on the same machine — this is a local door, not a
public one.

## Worked examples

Questions an assistant can answer once it is connected. Nothing here needs you to know an id, a
table, or a screen — the assistant starts from a list and drills in.

- *"List my MCP servers and tell me which one costs the most tokens before a model has done any
  work."*
- *"Take my newest scan of the Filesystem server. Which five tools are the most expensive, and what
  share of the total are they?"*
- *"Will that server fit inside GPT-5 and Claude Haiku, or will it strain them?"*
- *"Show me the test runs that failed this week, then explain what went wrong in the last one."*
- *"Pull the full report for that run and summarise the grades."*
- *"What does my `pdf-tools` skill cost, and does it bundle any scripts or reach out to the
  network?"*
- *"Compare the latest suite run's members — which combination was most expensive per graded
  point?"*

Two habits make the answers better: name a real thing ("the Filesystem server", "the pdf-tools
skill") so the assistant can find it, and ask it to **cite the numbers** it used, so you can check
them on the matching screen.

## The read-only guarantee

This door only reads. Connected assistants **cannot**:

- start a scan, launch a test run, or kick off a suite;
- change any setting, server, skill, or collection;
- delete anything;
- see a secret. Server credentials, request headers, and GitHub tokens are never returned — an
  assistant can see *that* a server has a secret configured, never what it is.

That is deliberate, not an oversight. An agent operating unattended has nobody to ask before it
spends money or removes data, so the first version of this door reads only. Writing is a separate,
explicitly permissioned step that is **not built yet** (see [What is not here yet](#what-is-not-here-yet)).

If you want an assistant that *can* act on your behalf inside the app, that is the built-in
[App assistant](./12-assistant.md), which asks you for approval before it changes anything.

## Turning it on and off

The door is a feature switch like any other: **Settings › Features › Workbench MCP server**.

Turn it off and the endpoint stops answering immediately — a connected assistant, a stale terminal,
or a script all get a plain "this feature is turned off" refusal, and the setting survives a
restart. Nothing else in the app changes: this feature has no screen and no menu entry of its own,
so switching it off simply closes the door.

Turn it back on and connected assistants can reconnect without any further setup.

## What it costs a model

Every MCP server a model connects to spends part of the model's context just *describing itself* —
which is the cost this whole app exists to measure. The workbench holds itself to the same standard
it holds your servers to: its own description is kept under a **3,000-token budget**, and a check
that runs with the test suite scans this very endpoint with the app's own scanner and fails if it
grows past it. The current measurement is **21 tools costing 2,224 tokens**.

You can reproduce that number yourself from the project folder:

```bash
pnpm mcp:self-scan
```

It writes a footprint report (JSON and Markdown) under `.artifacts/mcp-self-scan/` and prints the
measured total.

## What is not here yet

Being honest about the edges:

- **No actions.** Starting scans, launching runs, and running suites over this door are planned and
  not built. Use the app, or the [App assistant](./12-assistant.md), for anything that changes
  something.
- **No access tokens.** There is no per-assistant credential yet, which is exactly why this stays a
  local-machine door. Do not publish the port.
- **Local only.** Sharing a workbench with a team is a separate piece of work.
